# SaaS 출시 3개월 실행 계획 (Cloud-brain → 멀티테넌트)

기록 시점: 2026-06-15. 브랜치: `feat/cloud-brain`.
이 문서는 폰 연동(Telegram + Fly.io) → 멀티테넌트 SaaS 출시까지의 **시간 계획**이다.
(데스크톱 아바타/음성 기능 백로그는 `docs/ROADMAP.md` 별도.)

> **갱신(2026-06-15)**: 인프라 척추(Phase 4b~8)가 계획보다 빠르게 **코드 완료**됐고,
> 폰 데모는 Fly에 **실제 배포·가동 중**(캘린더 36건 동기화·봇 응답 확인). 아래 타임라인의
> Sprint 1·2·5는 코드상 끝난 상태 → "다음 우선순위"는 ‘실제 진도 vs 계획’ 절 참조.

> 최종 목표 = **일반 소비자 대상 멀티테넌트 SaaS, (a) 공유 Core 방식 100% 확정.**
> 격리 = 전 테이블 `user_id` + 공유 Core 한 프로세스가 전 유저 처리.

## 실제 진도 vs 계획 (2026-06-15 갱신)

인프라(Phase 4b~8)를 계획보다 앞당겨 끝냈다. 그 결과 **타임라인의 Sprint 1·2·5(=인프라/컷오버)는
코드상 완료**, 대신 **제품 가치 작업(Sprint 3·4)과 출시 전 테넌트 안전 마감이 비어 있다.**
즉 "더 많은 인프라/인증"이 아니라 **‘쓸 만한 제품 + 안전’이 다음**이다.

### 다음 우선순위 (이 순서)
1. **도그푸딩** — 폰 봇을 며칠 실사용하며 거슬리는 점 수집. (계획서 Milestone A 직후 의도)
2. **Sprint 3: 캘린더 신뢰성 + 비용 캐싱** — 패널 캘린더 뷰, 추가/수정/삭제 전수 검증,
   단순 빈시간 배치, FAQ 캐싱(캐시 키에 `user_id`).
3. **테넌트 안전 잔여 2건** (남 들이기 전 필수, ‘교차 관심사’ 절 참조):
   - Google 토큰 전역 → **per-user 암호화 테이블 + aes-gcm**
   - **speech 비용 `user_id` 명시 주입** (현재 `cost_ledger` DEFAULT 1 의존)
   - (참고: conversation_id 스코프·메모리 `user_id` 필터는 4a에서 이미 처리됨)
4. **얇은 멀티유저 온보딩** — 텔레그램 `/start` 딥링크로 user 행 생성 + chat-id↔user_id 매핑.
   + **유저별 비용 상한 enforce 확인**(4a에 토대 있음) + 초대/웨이트리스트 게이팅.
   → 친구 베타가 *자기 데이터로 격리되어* 사용 = 멀티테넌트 실사용 검증.
5. **풀 현관문**(웹 회원가입/로그인·호스티드 OAuth·결제) — 가치 검증 후. 한국 채널(카톡/PWA) 재결정.

> 결론: "인증 먼저"는 과함(솔로·비용부담·수요 미검증). 토대(`user_id`)는 이미 깔렸으니
> 인증은 *덧붙이기*. 4번(얇은 링킹)으로 실제 유저 경로를 싸게 검증한 뒤 5번(풀 현관문).

### 데스크톱 컷오버(Phase 7·8) 활성화 — 코드 완료, 운영 대기
`fly secrets set PA_GATEWAY_TOKEN=...` + `fly deploy` → 데스크톱에 `PA_CORE_MODE=remote`/
`PA_GATEWAY_URL`/`PA_GATEWAY_TOKEN` 환경변수. 상세는 `docs/CLOUD-DEPLOY.md` 8절. (라이브 검증 미완.)

## 운영 원칙

1. **흔들리는 토대 위에 기능 얹지 않기** — 마이그레이션 척추(4b~6)를 먼저 굳힌다.
2. **두 트랙 병렬** — 개발자=Core/임계경로, 오너=비코드(홈페이지·에셋·BM·Fly·온보딩).
3. **데모 게이트로 전진** — 매 마일스톤에 "작동하는 무언가".
4. **비용·테넌트 안전은 상시** (아래 교차 관심사 참조).

## 타임라인 (2주 스프린트 × 6 ≈ 3개월)

### Sprint 1 (wk 1–2) — 4b: 쓰기 Core 이관 + 누수 2곳
- 개발자: `chat.continue` 계약(result→approved), `execute_write_tool`(flat→nested 어댑터 + `buildEventPatch` Rust 포팅), 중복승인 가드, 실패 LLM 피드백, 렌더러 쓰기 제거. **+ `conversation_id` 충돌·메모리 자동주입 `user_id` 필터.**
- 오너: Fly 세팅 마무리 + BotFather 봇 생성 + 홈페이지 와이어프레임·문구 초안.
- **게이트**: 데스크톱 승인→Core 생성, 격리 테스트(messages·memories) 통과.

### Sprint 2 (wk 3–4) — Phase 5 봇 + Phase 6 Fly 배포
- 개발자: 텔레그램 봇 어댑터 + Dockerfile/fly.toml + Phase 3 토큰 이식(운영).
- 오너: 아바타 프리셋 에셋 준비 + 온보딩 UX 설계(QR 딥링크 방식).
- 🎯 **Milestone A: 작동하는 v0 — PC 꺼도 폰에서 채팅·캘린더·메모리·알림.** → 오너+소수 베타 도그푸딩 시작.

### Sprint 3 (wk 5–6) — 스케줄링 기본기(신뢰성) + 비용 캐싱
- 개발자: 패널 실제 캘린더 뷰, 추가/수정/삭제 전수 검증, 단순 빈시간 배치. + FAQ 캐싱(**캐시 키에 `user_id` 포함 = 테넌트 세이프**; 이미지·TTS도 cost_ledger에).
- 오너: 베타 피드백 수집, 홈페이지 제작 착수.
- **게이트**: 캘린더 CRUD가 폰·데스크톱서 안정. 캐시 히트로 비용 절감 측정.

### Sprint 4 (wk 7–8) — 아바타 베이스라인 + 음성 개인화 1차
- 개발자: 프리셋 아바타 + 동작별 슬롯 UI + 유저별 저장(`user_id` 있음 → 오브젝트 스토리지 도입). + 말투/개인화 1차.
- 오너: 튜토리얼 콘텐츠 제작, 가격/구독 확정.
- **게이트**: 유저별 아바타 저장·표시, 베타 "정든다" 반응.

### Sprint 5 (wk 9–10) — Phase 7+8 데스크톱 컷오버
- 개발자: WS 게이트웨이(Tailscale) + remote-client → 풀 연속성(폰·데스크톱 같은 대화·메모리) + 알림 이중발화 해소.
- 오너: 홈페이지 완성, 업데이트/Contact 채널.
- 🎯 **Milestone B: v0.5 풀 연속성** — 데스크톱도 클라우드 클라이언트.

### Sprint 6 (wk 11–12) — 현관문 백엔드 1차
- 개발자: 회원가입/인증 + 호스티드 OAuth(유저가 직접 구글 연동) + 텔레그램 계정 링킹. (결제는 다음.)
- 오너: 베타→오픈 준비, 출시 공지.
- 🎯 **Milestone C: 모르는 유저가 가입→연동→사용 가능** → 무료/웨이트리스트 출시 가능.

## 확정 결정 (그동안 합의)

- **폰 대화 = 데이터 공유 + 채팅 스레드 분리** (Phase 5에서 확정, 계획서 초안의 "옵션 2 default 공유"에서 변경).
  실제 구현: `user_id=1`로 **todos·메모리·캘린더는 공유**, 채팅 로그만 `conversation_id="tg:<chatId>"`로 분리.
  이유: 데스크톱 채팅 버블과 폰 대화가 한 스레드에 섞이지 않게. 기기 넘나드는 *데이터* 연속은
  user_id로 이미 보장되고, *대화 맥락* 통합은 Phase 8 컷오버 이후 정책으로. `(user_id, conversation_id)`
  스코프(4a)가 떠받침. (전송 계층 무변경 — 봇이 user_id 생략 → Core가 1로 귀착.)
- **텔레그램 = v0 채널 한정.** BotFather/secrets 복잡함은 오너 1회 몫이고, 유저 온보딩은 QR 딥링크로 ~2탭. 단 **한국 일반 유저는 카카오톡 사용** → 공개 출시 채널은 현관문 단계에서 재결정(후보: 카카오 / PWA / 네이티브 앱). 클라이언트가 얇아 채널 추가는 "또 하나의 얇은 클라이언트"라 저비용.

## 교차 관심사 (상시)

### 비용 (BM = API 비용 자체 부담)
거의 모든 기능이 비용 ↑(고급 모델·이미지 생성·TTS·스케줄링 호출). 유일한 ↓는 **FAQ 캐싱**. → 유저별 비용 상한 + 캐싱 + 기본은 싼 모델 + 비용 가시성을 1급으로. 이미지·TTS도 cost_ledger 편입.

### 테넌트 안전 (출시 전 반드시 해소 — 4a에서 미룬 지점)
1. Google 토큰 전역 SecretsStore 유지 → per-user 암호화 테이블 + aes-gcm.
2. speech cost가 `cost_ledger user_id DEFAULT 1`에 암묵 의존 → 명시 주입.
3. `conversation_id` 유저 간 충돌 → `(user_id, conversation_id)` 스코프(4b에서 처리).
4. 메모리 검색/시스템 프롬프트 자동 주입의 `user_id` 필터.
5. 신규 캐싱·유저별 이미지도 누수 재발 지점 — `user_id` 스코프 필수.
