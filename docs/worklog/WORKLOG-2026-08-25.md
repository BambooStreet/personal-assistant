## 발단 — "할 일 목록"이 응답 없이 사라진 것처럼 보인 사건

데스크톱에서 "할 일 목록"을 쳤는데 아무 응답도 안 보였다. 조사해 보니 **서버는 정상이었다.**

클라우드 `messages` 테이블에 그 턴이 그대로 남아 있었다 — 16:40:09 사용자 메시지 → 16:40:19
`list_todos` 호출 → 16:40:**32** "할 일 7건이에요…". **23초** 걸렸을 뿐 정상 응답이었다.
두 번째 시도(16:50)도 19.4초로 똑같이 성공했다. "갑자기 잘 된다"가 아니라 그때는 끝까지
기다린 것이었다.

**진짜 문제는 진단 자체가 불가능했다는 것.** `fly logs`에도 `/data/logs/core.log`에도 채팅은
한 줄도 안 찍혀 있었고(배경 캘린더 동기화와 알림뿐), 패키징 앱은 원격 모드라 로컬 `core.log`도
없다. 결국 프로덕션 DB를 직접 조회해서야 답이 나왔다. 그 23초 동안 **클라이언트에서** 무슨 일이
있었는지는 끝내 복원하지 못했다.

### 릴리스 노트 자동 생성

v0.1.1~v0.1.4는 릴리스 본문이 전부 비어 있었다 — electron-builder는 태그·제목·에셋만 만들고
본문은 안 채운다. `release-desktop.yml`에 `Fill release notes` 스텝을 붙였다.

- GitHub 기본 자동 노트(`--generate-notes`)는 **머지된 PR 기준**인데 이 저장소는 main에 직접
  커밋한다(PR은 6월 이후 0건) — 그래서 직전 태그 이후 **Conventional Commits**를 직접 묶는다.
  `feat` → "새 기능", `fix` → "고친 것", scope는 굵게. 끝에 compare 링크.
- `actions/checkout`에 `fetch-depth: 0` 필요 — 기본 depth 1이면 `git describe`가 직전 태그를
  못 찾아 범위가 비어버린다.
- 본문이 이미 있으면 건너뛴다 — 손으로 쓴 노트를 재실행이 덮어쓰지 않도록.
- v0.1.5 본문은 수동으로 붙여넣었다(이 스텝은 다음 태그부터 적용).
